Project Review

Laravel Best Practices Report

This document captures the current Laravel best-practices review for the project, highlights where the codebase deviates from common framework guidance, and records the two deliberate choices that were explicitly kept for this application.

Scope

  • Focused on current application code and framework usage patterns.
  • Did not change any source files as part of this review.
  • Included recommendations for each issue that is still open.

Deliberate Decisions

  • Cache object serialization remains an explicit tradeoff for performance.
  • Deterministic encrypted IDs are intentionally kept to avoid breaking existing requests.
High

Encrypted-ID Contract Is Inconsistent In Some API Resources

Some resources expose raw numeric foreign keys and also build related links using those numeric IDs, even though the project uses encrypted public IDs in routes. That creates an inconsistent API contract and can produce broken or misleading related links.

  • app/Http/Resources/Product/ProductCollection.php
  • app/Http/Resources/Product/ProductResource.php
  • app/Http/Resources/Transaction/TransactionCollection.php
  • app/Http/Resources/Transaction/TransactionResource.php

Suggested Fix

  • Expose the same public identifier format everywhere a related model ID appears in an API response.
  • Generate related links with the same encrypted/public ID value used by route model binding.
  • Audit all API resources for raw foreign keys so the contract stays consistent across collections and single resources.
High

User List Cache Can Become Stale After Creating A User

The user creation flow stores the new record but then uses Cache::remember() against the list cache key. If the list is already cached, Laravel keeps the old cached payload, so the newly created user may not appear until the cache expires or is manually cleared.

  • app/Http/Controllers/User/UserController.php

Suggested Fix

  • Forget the list cache key after writes so the next read repopulates it with fresh data.
  • Or replace remember() with a cache write that overwrites the key immediately after create/update/delete.
  • Cover the write path with a focused feature test that proves the list reflects a newly created user.
Medium

Several Index Endpoints Load Entire Tables Into Memory

Multiple controllers load complete model tables with all() and only then apply filtering, sorting, and pagination in memory. That works for small datasets, but it moves work away from the database and makes endpoint performance degrade as data grows.

  • app/Http/Controllers/User/UserController.php
  • app/Http/Controllers/Category/CategoryController.php
  • app/Http/Controllers/Buyer/BuyerController.php
  • app/Http/Controllers/Product/ProductController.php
  • app/Http/Controllers/Seller/SellerController.php
  • app/Http/Controllers/Transaction/TransactionController.php

Suggested Fix

  • Move filtering, sorting, and pagination to the query builder where possible.
  • Reserve in-memory processing for cases that truly cannot be expressed in SQL.
  • If caching is still needed, cache query-level results or paginated payloads rather than entire model tables.
Medium

Validated Requests Are Not Always Used Safely

A few controllers persist data from $request->all() even though the project already uses Form Request classes. That makes the write path broader than necessary and bypasses the cleaner Laravel pattern of using validated input only.

  • app/Http/Controllers/User/UserController.php
  • app/Http/Controllers/Category/CategoryController.php
  • app/Http/Controllers/Seller/SellerProductController.php

Suggested Fix

  • Switch write operations to $request->validated() when a Form Request is already in place.
  • Keep controllers thin and let Form Requests remain the source of truth for accepted fields.
  • Add tests for ignored/unexpected fields on create and update endpoints.
Medium

env() Is Used In Runtime Application Code

The application checks env('APP_ENV') directly in the service provider. Laravel recommends keeping environment lookups inside configuration and reading them through config() or framework helpers at runtime.

  • app/Providers/AppServiceProvider.php

Suggested Fix

  • Move the environment-dependent value into a config file and read it via config().
  • Or use framework helpers like app()->environment() when the intent is environment detection.
Tradeoff

Cache Serialization Hardening Was Relaxed Intentionally

The cache configuration allows serializable classes so the original raw-object caching pattern continues to work efficiently. This is an explicit tradeoff that was chosen for this project, not an accidental regression.

  • config/cache.php

Context

  • This choice favors compatibility and performance of the current caching strategy.
  • The tradeoff is reduced alignment with the framework’s safer default cache hardening.
  • No fix is required unless the project later decides to move back to the stricter framework behavior.
Intentional

Deterministic Encrypted IDs Are Kept On Purpose

The custom encrypted-ID approach is intentional. If the project stopped using deterministic encrypted IDs, the public identifiers would change over time, existing requests would no longer resolve reliably, and clients depending on stable request URLs would break.

  • app/Helpers/globalFunctions.php

Context

  • This is a deliberate stability decision for the existing request contract.
  • No immediate change is recommended unless the project plans a coordinated migration to another public ID strategy.
  • If that migration ever happens, it should include backward-compatibility planning for existing consumers.

This report is intended to be a review artifact for the current codebase. It preserves the two explicitly accepted tradeoffs while keeping the remaining issues actionable and ready for follow-up work.
